# 4.13 — Direct-to-bucket entry video upload

**Status:** 🟢 Complete
**Branch:** feature/direct-video-upload
**Date:** 2026-09-22

## Overview

Creator entry submission crashed in production with a fatal error:

```
Allowed memory size of 268435456 bytes exhausted (tried to allocate 132120608 bytes)
at vendor/symfony/http-foundation/Request.php:1589
```

`StoreEntryRequest` accepted videos up to 200 MB (`max:204800`), but a multipart POST is buffered
by PHP before Laravel sees it, so anything approaching that size exhausted `memory_limit` during
request parsing — before any application code ran.

Videos now go **straight from the browser to the storage bucket** via a presigned `PUT`. PHP never
receives the body, so the upload is bound by neither `memory_limit`, `post_max_size` nor
`upload_max_filesize`. The cap rises from 200 MB (which never actually worked) to a real,
enforceable **500 MB**.

## Two upload paths

| Host | Condition | Path | Ceiling |
|---|---|---|---|
| Production (Laravel Cloud bucket) | default disk driver is `s3` | Presigned `PUT` direct to bucket | 500 MB |
| Local dev (`FILESYSTEM_DISK=local`) | no bucket attached | Multipart `POST` through PHP | 20 MB |

The local driver cannot sign upload URLs, so `DirectUpload::supported()` gates the behaviour and the
page falls back automatically. The fallback ceiling (`FALLBACK_MAX_KILOBYTES`) must stay under the
smallest of PHP's three limits — this is what the earlier 200 MB rule violated.

## Flow

1. Creator picks a file. The page checks it against the ceiling it was handed as a prop.
2. On submit, `POST /entries/upload-url` reserves a key (`entries/videos/{ulid}.{ext}`) and returns
   a presigned URL plus an HMAC **signature** binding that key to the creator.
3. The browser `PUT`s the file straight to the bucket, reporting progress.
4. The form submits `video_path` + `video_signature` instead of the file.
5. `DirectUpload::claim()` verifies the signature, confirms the object landed, and checks its size
   before the path is written to `entries.video_url`.

## Security

`video_path` arrives from the client, so it is never trusted on its own:

- **Forgery** — the path must carry an HMAC (`app.key`) issued by `reserve()`; `hash_equals` compares.
- **Cross-creator theft** — the HMAC binds the creator's user id, so a path signed for one creator
  cannot be claimed by another.
- **Path injection** — keys are generated server-side from a ULID. Only the *extension* comes from
  the client and it is checked against an allowlist (`mp4`, `mov`, `avi`, `webm`).
- **Dangling rows** — the object must exist on the disk before the path is accepted.
- **Size** — declared size is rejected at presign time; actual size is re-checked after upload and
  an oversized object is deleted.

**Known tradeoff:** because the bytes never reach PHP, the `mimes:` content check cannot run on the
direct path. The presigned URL is signed for a specific `Content-Type`, but a client could still PUT
mismatched bytes. Objects are only ever rendered into a `<video>` element. Server-side content
verification would need transcoding (out of scope).

## Implementation

- **`app/Support/DirectUpload.php`** — `supported()`, `maxBytes()`, `reserve()`, `claim()`, HMAC signing.
- **`app/Http/Controllers/Entry/VideoUploadUrlController.php`** — presign endpoint; extension
  allowlist → signed `Content-Type`.
- **`routes/entry.php`** — `POST /entries/upload-url` (`entries.creator.upload-url`).
- **`StoreEntryRequest`** — accepts `video_path` + `video_signature`; the `video` fallback is capped
  at `DirectUpload::FALLBACK_MAX_KILOBYTES`.
- **`CreatorEntryController`** — `resolveVideoPath()` resolves direct upload → multipart fallback →
  the file already on the draft, shared by `store()` and `resubmit()`. `create()` passes an `upload`
  prop (`direct`, `maxBytes`).
- **`resources/js/hooks/use-direct-upload.ts`** — reserve + PUT with progress.
- **`resources/js/pages/entries/creator/submit.tsx`** — uses the hook, shows a progress bar, and
  derives its size limit and hint text from the prop rather than a hardcoded number.

## Deployment requirement

⚠️ **The bucket needs CORS before the direct path works.** The browser issues a cross-origin `PUT`,
so the Laravel Cloud bucket must allow:

- Origin: the app's domain
- Method: `PUT`
- Header: `Content-Type`

Without it every direct upload fails at step 3. The page surfaces an error and does not silently
lose the entry, but uploads will not succeed until CORS is configured.

## Verification

`tests/Feature/Entry/DirectVideoUploadTest.php` — 8 passing:

- signs a URL scoped to the creator; rejects non-video extensions; rejects oversize before signing
- accepts a valid signed path once the object is present
- refuses a forged signature, a path signed for a different creator, and a path whose upload never landed
- falls back to the multipart ceiling when no bucket is attached

Build, `types:check` and Pint all pass.

**Not verified locally:** the browser → bucket `PUT` itself, since local dev has no bucket
(`FILESYSTEM_DISK=local`) and therefore uses the multipart fallback. The direct path needs a
CORS-configured bucket on staging/production to exercise end to end.
