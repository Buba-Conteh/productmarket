# 1.16 — Google & Phone (SMS OTP) Signup

**Status:** 🟢 Complete
**Branch:** feature/google-phone-signup

## Overview

Added two new ways to create an account / log in, alongside email + password:

1. **Google** — the OAuth flow already existed ([SocialAuthController](../../app/Http/Controllers/Auth/SocialAuthController.php))
   but was only surfaced on the login page and created users with **no role**.
   It's now offered on the register page too, and role-less social signups are
   routed to a new **role picker** before onboarding.
2. **Phone number** — passwordless **SMS OTP**: enter phone → 6-digit code →
   verify → (new account) pick role → onboarding.

Both new-account paths converge on the shared role-selection step, since neither
Google nor phone carries a Brand/Creator choice.

## Flow

```
Register/Login page
  ├── Continue with Google ─────► /auth/google/redirect ─► callback
  │                                   creates user (no role), logs in
  └── Continue with phone  ─────► /auth/phone
          enter phone ─► POST /auth/phone (OTP sent) ─► /auth/phone/verify
          enter code  ─► POST /auth/phone/verify
              verify OK ─► find-or-create user by phone, log in

Any logged-in user without a role
  └─ EnsureOnboardingComplete ─► /auth/select-role ─► assign role ─► onboarding
```

## Decisions

- **Passwordless SMS OTP** for phone (lowest-friction rollout; no password to
  manage for phone users).
- **Vonage** as the SMS provider (first-party Laravel channel, free trial credit),
  called via a plain HTTP request — no extra Composer package.
- **Stub mode** (`SMS_STUB_MODE`, default `true`) mirrors the existing
  `ESCROW_STUB_MODE` pattern: the OTP is written to the log instead of sent, so
  local/staging work with no paid SMS account.
- **Role asked after** Google/phone (not before), per the shared role picker.

Phone-only users get a random password, `email = null`, and both
`email_verified_at` + `phone_verified_at` set to now — so the `verified`
middleware and onboarding gate treat them as verified.

## Rate limiting / abuse

- `throttle:6,1` on send / verify / resend routes.
- Per-phone cooldown (`SMS_OTP_COOLDOWN`, default 60s) in `PhoneOtpService`.
- OTP is single-use, attempt-capped (`SMS_OTP_MAX_ATTEMPTS`, default 5), and
  expires after `SMS_OTP_TTL` (default 300s). Stored hashed.

## Verification

Smoke-tested the service + model flow directly: OTP send creates a record,
wrong code fails, correct code verifies, a consumed code can't be reused, and a
phone-only user with `email = null` passes `hasVerifiedEmail()` while
`hasSelectedRole()` is false (so it routes to the role picker). `npm run build`,
`tsc --noEmit`, ESLint (new files), and Pint all pass.

## Roles

Both **Brand** and **Creator** can sign up via Google and phone. Because Brand
billing (Stripe) and notifications need an email, the role picker requires an
email from any account that arrives without one (phone signups); Google signups
already carry a verified email and skip this field.

## Follow-ups (out of scope)

- An email added at the role-select step is trusted as-is (not re-verified) — the
  phone was the verified identity. A later step could send a verification email.
- Real Vonage delivery needs `SMS_STUB_MODE=false` + `VONAGE_KEY`/`VONAGE_SECRET`.
