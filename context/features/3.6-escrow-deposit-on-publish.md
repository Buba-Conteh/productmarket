# 3.6 — Escrow Deposit on Publish (real Stripe charge)

**Status:** 🟢 Complete
**Branch:** feature/escrow-paymentintent
**Date:** 2026-06-24

## Overview

Publishing a campaign now collects the escrow deposit from the brand via Stripe instead of
recording a placeholder. This completes the **brand → escrow (money IN)** leg, which pairs with
the already-built **escrow/platform → creator (money OUT)** leg in `PayoutService`.

Previously `CampaignService::publish()` / `republish()` wrote an `escrow_transactions` row with a
placeholder `stripe_payment_intent_id` (`pending_<campaign_id>`) and went straight to `active` —
no money was ever collected, so the platform Stripe balance was never funded by campaigns.

## Charge model

**Separate charges and transfers** (per Stripe best-practices for this escrow shape):

- Escrow is funded at the **campaign** level at publish time; recipients (creators) are unknown
  and can be many (contest winner + runner-up, ripple milestones across creators).
- The brand is charged into the **platform's** Stripe balance now.
- Creators are paid later from that balance via `transfers->create` (`PayoutService`, unchanged).

Destination charges were rejected because they route to a single connected account at charge time.

## Implementation

- **`config/escrow.php`**
  - `stub_mode` (env `ESCROW_STUB_MODE`, default `true`)
  - `currency` (env `ESCROW_CURRENCY`, default `usd`)
- **`CampaignService::fundEscrow(Campaign, float): string`**
  - Stub mode → returns a `pending_<id>_<ts>` placeholder (unchanged dev/test behaviour).
  - Real mode → validates brand has a Stripe customer + default payment method, then charges
    off-session via Cashier `charge()`, returns the real PaymentIntent ID.
  - Charge runs **before** the DB transaction. Aborts 422 with a brand-facing message on
    failure or when SCA (`IncompletePayment`) is required.
- **`publish()` / `republish()`** use `fundEscrow()` for the stored PaymentIntent ID.
- Refund path (`issueStripeRefund`) already skips `pending_*` IDs, so stub escrows are unaffected
  and real (`pi_*`) escrows now refund correctly on cancellation.

## Verification

`php artisan payout:verify-flow` drives the real contest-completion → Connect transfer against
Stripe **test** mode. Extended with:

- `--connect=acct_...` to reuse an existing onboarded test account (verifies transfers capability).
- `--prize=` to control the amount.
- Available-balance pre-check and a queue-worker note.

Confirmed end-to-end in test mode: contest completion fired a real transfer to the connected
account, creator `total_earned` and escrow `total_released` updated, payout marked `paid`.

## Staging prerequisites

1. `ESCROW_STUB_MODE=false` + Stripe test keys.
2. Brand subscribed (saved default payment method).
3. Creator Connect account active (`stripe_connect_status = active`).
4. Queue worker / Horizon running (`ProcessPayoutJob` is queued).
5. Payout ≥ `min_creator_payout` ($25).
6. Charges land in Stripe **pending** balance first, **available** on a rolling delay.

## Follow-ups (not in this change)

- Webhook reconciliation for escrow charges (`payment_intent.succeeded/failed`).
- Brand-facing UI to handle SCA / failed escrow charge at publish time (currently a 422).
- `payout:verify-flow` is a manual diagnostic command — consider removing or moving to a seeder.
